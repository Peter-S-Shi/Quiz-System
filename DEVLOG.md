# Development Log

## 2026-08-10

- Implemented M6.5 Rich Correction / Revision Workspace: a reviewer (the learner or a human teacher) can open a finalized Translation Learner Response, see the immutable original answer and M6.4 learner marks read-only, and add structured rich correction evidence without ever mutating the underlying evidence.
- Added `src/core/corrections.js`: a single `correction` concept (`operation`, anchor `start`/`end`, `anchoredText`, operation-specific `text`/`styleType`/`color`, `createdAt`) covering presentation styles (bold, italic, underline, strikethrough, highlight, bracket, text color) and content-changing operations (insert, replace, delete), plus span/whole-item comments. Presentation styles are orthogonal and may overlap each other and any content-changing operation; content-changing operations may never overlap each other, and `addCorrection()` throws on a conflicting add rather than silently applying it — surfaced in the UI as a toast, matching the M6.4 marking pattern. `renderCorrectionProjection()` turns an answer plus its corrections into an ordered list of render segments (styled/plain text runs, struck-through deleted/replaced original text, inserted/replacement text) that the UI renders through `escapeHtml()`, so reviewer or inserted text is never injected as raw HTML.
- Extended the existing M6.0 Teacher Review contract additively: `itemReviews[].corrections` is a new optional array (also added to `schemas/teacher-review.schema.json` as an optional property with a `correction` definition), so existing simple Teacher Reviews (judgment/comment/tags/suggestedRevision only) remain valid and unchanged; `suggestedRevision` is preserved and can coexist with rich correction on the same item.
- Extended `validateTeacherReview()` with runtime cross-field validation for corrections: each correction's anchor is checked against the corresponding Learner Response's answer text (unknown item, out-of-range, and anchored-text-mismatch all fail validation), and content-changing operations that conflict on the same item are rejected — this stays a runtime responsibility since the public JSON Schema cannot express "must match sibling data," matching the pattern established by the M6.4 `learnerAnnotations` integrity patch.
- Added `src/core/review-records.js` (mirroring `learning-records.js`): an independent Teacher Review collection with no silent history cap, keyed by stable review ID with a stable `responseId` relationship. `upsertTeacherReview()` allows updating a review's content in place (unlike the immutable Learner Response) but throws if an existing review ID would be silently reassigned to a different response.
- Added a new `quiz-studio-teacher-reviews-v1` storage key and extended `createLibraryBackup()`/`parseLibraryBackup()` to include Teacher Reviews in full-library backups; legacy backups without them remain valid, and malformed review data fails safely (via a thrown error) before any state is applied, matching the existing Learner Response backup-safety pattern.
- Added the Correction Workspace UI to `src/app.js`: reachable from the Translation Practice completion screen and from a new minimal "Finalized responses" list on the Translation Document editor (deliberately not a full history browser, which is scoped to M6.7). The original answer renders in a `readonly` textarea (not `contenteditable`) so native text selection works for choosing correction spans without any risk of mutating the evidence; a live preview below the toolbar shows the corrected rendering using `renderCorrectionProjection()`.
- Expanded automated coverage from 73 to 110 passing tests with new `tests/corrections.test.js` and `tests/teacher-review-corrections.test.js`, covering every style/operation type, orthogonal-style overlap, content-op conflict rejection, anchor mismatch/out-of-range/duplicate-ID rejection, HTML-like text safety, review persistence/reload/no-silent-reassignment, backup/restore round-trip and legacy/malformed-data handling, and compatibility with M6.0 simple reviews, M6.4 annotated responses, older unannotated responses, and Objective Quiz responses; all earlier tests continue to pass unchanged.

- Closed a small M6.4 annotation-integrity gap before starting M6.5. `normalizeAnnotationList()` previously validated each persisted annotation independently, so two individually valid but overlapping (or exact-duplicate-span) marks could both survive session recovery even though normal marking through `addAnnotation()` never allows that. Normalization now keeps annotations in persisted order and drops any candidate that overlaps one already kept, so recovery always converges on the same overlap-free result as live use.
- Closed a matching gap in finalized evidence: `validateLearnerResponse()` previously checked each `learnerAnnotations[]` entry's own fields (kind, range shape, id/itemId) but never cross-checked an entry against the learner answer it claims to anchor. It now verifies, per annotation, that the referenced `itemId` has a corresponding response with a string answer, that the range falls within that answer, that `answer.slice(start, end)` equals the recorded `text`, and that no two annotations on the same item overlap. A structurally well-formed but tampered or externally supplied Learner Response (wrong anchor text, out-of-range span, or overlapping marks) now fails runtime validation instead of passing on shape alone. `schemas/learner-response.schema.json` is unchanged; this cross-field check is intentionally a runtime-only responsibility, as anchor text depends on sibling `responses[]` data the static schema cannot see.
